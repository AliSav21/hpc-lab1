# Реєстр донорів: CRUD-сервіс і вимірювання масштабованості

Навчальний проєкт з дисципліни «Високопродуктивні розподілені обчислювальні системи».
Три лабораторні роботи в одному репозиторії: кожна наступна доповнює сервіс, написаний у ЛР1,
а не замінює його.

Стек: Python 3.12, FastAPI, psycopg 3 (пул зʼєднань), PostgreSQL 16, nginx 1.27, Prometheus,
Docker Compose, а в ЛР3 — Kubernetes (kind), kube-prometheus-stack і HorizontalPodAutoscaler.
Генератор навантаження і всі скрипти вимірювань — лише стандартна бібліотека Python
(matplotlib потрібен тільки для діаграм).

## Три лабораторні і два варіанти

| | Лабораторна 1 | Лабораторна 2 | Лабораторна 3 |
|---|---|---|---|
| Про що | спроєктувати й розгорнути CRUD-сервіс у Docker Compose, зміряти пропускну здатність | додати метрики Prometheus, зміряти X(N) на 1–4 екземплярах, визначити параметри закону масштабованості | перенести сервіс, базу і моніторинг у Kubernetes, зміряти X(N) і дисбаланс у кластері, порівняти фіксовані репліки з HorizontalPodAutoscaler |
| Варіант | **20** | **19** | **19** |
| Звіт | [REPORT.md](REPORT.md) | [REPORT-LAB2.md](REPORT-LAB2.md) | [REPORT-LAB3.md](REPORT-LAB3.md) |
| Запуск | [RUN.md](RUN.md), детально [HOWTO.md](HOWTO.md) | [RUN-LAB2.md](RUN-LAB2.md) | [RUN-LAB3.md](RUN-LAB3.md), детально [HOWTO-LAB3.md](HOWTO-LAB3.md) |
| Тег у git | `lab1` | `lab2` | `lab3` |

**Про номер варіанта.** ЛР1 виконана за варіантом 20: сутність «запис реєстру донорів», ресурс
`/donor-registry`, фільтр за доступністю, валідація віку 18–55, ліміти контейнера 1 CPU і 512 МБ.
ЛР2 виконана за варіантом **19**: розмір пулу зʼєднань 10, набір бакетів гістограми Г1
(5, 10, 25, 50, 100, 250, 500, 1000 мс), додаткова метрика М1 (зайнятість пулу і час очікування
зʼєднання). Ліміти CPU і памʼяті взяті з ЛР1 і не змінювались, як того вимагає умова ЛР2. Сам
сервіс під варіант 19 не переписувався.

ЛР3 виконана за тим самим варіантом **19**: R = 4 репліки, кластер kind (один вузол control-plane
і два worker), `requests.cpu` 500m і `limits.cpu` 1, цільове використання CPU для HPA 50 %,
рівень стрибка min(1,5·X(1), 0,9·X(R)), додаткова вимога Д1 — рівномірний розподіл подів по двох
робочих вузлах через `topologySpreadConstraints`.

## Структура проєкту

### Сервіс і стенд

| Шлях | Навіщо |
|---|---|
| `app/main.py` | весь сервіс: 6 ендпоінтів CRUD, валідація, пул зʼєднань, метрики Prometheus, `/healthz`, `/livez`, `/metrics` |
| `db/schema.sql` | схема таблиці `donor_registry`; накочується автоматично при першому старті порожньої бази |
| `Dockerfile` | багатоетапна збірка на `python:3.12-slim`: залежності у venv, у фінальному образі немає компіляторів, `curl` і `wget` |
| `.dockerignore` | що не потрапляє в контекст збірки |
| `docker-compose.yml` | стенд: `db`, `web` (N реплік), `lb`, `prometheus` |
| `lb/nginx.conf` | балансувальник: round-robin по екземплярах, `/noop` для заміру межі генератора |
| `prometheus/prometheus.yml` | збір метрик кожні 5 с, пошук екземплярів через DNS Compose |
| `requirements.txt` | залежності сервісу |
| `requirements-dev.txt` | matplotlib — лише для побудови діаграм, у контейнер не потрапляє |

## Базові команди

Усе запускати з кореня репозиторію.

### Підняти стенд

```bash
cp .env.example .env
```

У `.env` задати `POSTGRES_PASSWORD`, далі:

```bash
docker compose up -d --build
```

Сервіс: `http://127.0.0.1:18080` (порт `LB_PORT`). Prometheus: `http://127.0.0.1:19090` (порт
`PROM_PORT`). Порт публікує лише балансувальник — база і екземпляри `web` з хоста недоступні.

### Кілька екземплярів

```bash
docker compose up -d --scale web=4
```

Якщо кількість екземплярів змінюють на **вже запущеному** стенді, потрібен ще
`docker compose restart lb`: nginx розвʼязує імʼя `web` один раз при старті.

### Корисні запити

```bash
curl http://127.0.0.1:18080/healthz
```

```bash
curl http://127.0.0.1:18080/metrics
```

`/healthz` — готовність (503, поки база недоступна), `/livez` — живість процесу без звернення до
бази, `/metrics` — метрики Prometheus, `/docs` — опис API.

### Вимірювання ЛР1

```bash
python loadgen/run_series.py series --instances 1
```

```bash
python loadgen/aggregate.py
```

### Вимірювання ЛР2





### Зупинка

```bash
docker compose down
```

Дані лишаються. Щоб прибрати разом із томами (база і дані Prometheus):

```bash
docker compose down -v
```

## Про порт 18080

На Windows `localhost` розвʼязується і в `127.0.0.1`, і в `::1`, і зайнятим може бути лише один із
них — тоді запити тихо йдуть на чужий сервер. Тому в `.env.example` узято непоширений порт, а всі
скрипти звертаються явно до `127.0.0.1`. Перевірити зайнятість:

```bash
netstat -ano | findstr :18080
```

## Застереження до чисел

Генератор, стенд і Prometheus працюють на одній машині й конкурують за ядра. У ЛР2 це вийшло
основним висновком: вузьке місце — процесор хоста, і через це результати погано відтворюються між
прогонами. Серію проведено чотири рази, усі результати наведені в розділі 7
[REPORT-LAB2.md](REPORT-LAB2.md).

У ЛР3 те саме застереження діє ще сильніше: кластер із трьох вузлів, база, моніторинг і генератор
ділять ті самі вісім ядер, а запити додатково проходять через опублікований порт Docker Desktop,
kube-proxy і мережу між вузлами. Серію знято тричі, розкид між прогонами наведено в розділі
Розкид між серіями [REPORT-LAB3.md](REPORT-LAB3.md); абсолютні X(N) там мають похибку порядку
чверті, тому σ і κ слід читати як оцінку порядку величини.
