## 0. Умови вимірювання (прочитати перед числами)

- Усе (генератор, nginx, Postgres, вебінстанси і VM Docker Desktop) працює **на одній машині**: Windows 11, 8 логічних
  ядер, 15,8 ГБ ОЗП, Docker Desktop (WSL2, 8 CPU, 8 ГБ). На верхніх рівнях вони **конкурують за ядра**.
- Генератор запускався з 4 процесами (половина логічних ядер) по 64 потоки у відкритому контурі.
- «Досягнута інтенсивність» це кількість отриманих відповідей за секунду всередині 30-секундного вікна вимірювання.
- Затримка міряється від **запланованого** моменту відправки, тож черга, що накопичилась, видна в перцентилях.
- Після кінця прогону генератор чекає ще 15 с; запити, що не завершились, записуються як невдалі (статус `-1`),
  їхня затримка це час до дедлайну. Тому колонка «не-2xx» на рівнях 800 і 1000 це **незавершені запити, а не відповіді
  5xx**, а p95/p99 там слід читати як нижню межу.
- У режимі перевантаження результат залежить від фонового навантаження хоста. Перший прогін рівня 1000 (з відкритим
  браузером) дав 563 rps на одному інстансі і 789 на двох; повторний, на тихішій машині, дав 540 і 591. Повтори
  2×1000 також різняться між собою (664, 591, 432). Тому нижче наводяться всі три значення, а не лише медіана.

### Колізія порту 8080 і чому вона не зіпсувала результати

Під час контрольної перевірки виявилось, що на цій машині порт 8080 на `0.0.0.0` з 15.09.2026 займає сторонній процес
`ApplicationWebServer`, а Docker публікував балансувальник на IPv6 (`::` і `::1`). Імʼя `localhost` на Windows
розвʼязується і в `::1`, і в `127.0.0.1`, тому частина зʼєднань могла потрапити не на наш nginx, а на чужий сервер,
який миттєво віддає 404.

Проблема проявилась лише в одному прогоні (закритий контур на asyncio, який обрав IPv4) і була помічена за
неможливо високою пропускною здатністю при 404 у відповідях. Усі сирі файли прогонів перевірено на наявність
сторонніх відповідей:

```
файл                                       200     404  conn-err(0)  незавершені(-1)
1x\rate10_r1..r3                           400       0            0                0
1x\rate100_r1..r3                         4000       0            0                0
1x\rate500_r1..r3                        20000       0            0                0
1x\rate700_r1..r3                       19000+       0            0            0..700
1x\rate800_r1..r3                      23409..       0            0        4761..8591
1x\rate1000_r1..r3                     28765..       0            0       9434..11235
2x\rate10..rate1000                       усі        0            0      лише -1 на 1000
selfcheck\rate500, rate1000         10000/20000      0            0                0
closed\rate500_c110_r1..r3               24647+      0            0                0
```

Жодного 404 і жодної помилки зʼєднання в основних серіях немає, тож усі числа цього звіту зняті саме з нашого стенду.
Після виявлення колізії стенд переведено на порт `18080`, а всі скрипти звертаються явно до `127.0.0.1`, а не до
`localhost`, щоб прибрати неоднозначність IPv4/IPv6.

## 1. Етап 1. Проєктування: схема таблиці

Таблиця `donor_registry` (файл `db/schema.sql`, накочується автоматично при першому старті бази):

| Поле | Тип | Обов'язкове | Обмеження |
|---|---|---|---|
| `id` | `BIGINT GENERATED ALWAYS AS IDENTITY` | так | PRIMARY KEY, генерує база |
| `donor_code` | `TEXT` | так | UNIQUE |
| `birth_year` | `SMALLINT` | так | CHECK 1900..2100 |
| `blood_group` | `TEXT` | так | CHECK у (O+, O-, A+, A-, B+, B-, AB+, AB-) |
| `hla_typing` | `TEXT[]` | так | CHECK кількість елементів >= 1 |
| `registered_on` | `DATE` | так | |
| `available` | `BOOLEAN` | так | |

**Індекси.** PRIMARY KEY на `id`; `UNIQUE (donor_code)`; складений `idx_donor_registry_available_id (available, id)`.
Останній обслуговує запит переліку `WHERE available = $1 ORDER BY id LIMIT ... OFFSET ...`: фільтр і стабільний
порядок для пагінації виконуються по одному індексу.

**Чому такі типи.**
- `id` як `BIGINT IDENTITY`: клієнт його не передає, генерує база; `GENERATED ALWAYS` забороняє явне вставлення.
- `birth_year` як `SMALLINT`: потрібен лише рік, вік рахується від нього; `DATE` додав би зайві день і місяць.
- `blood_group` як `TEXT` + `CHECK`: закритий перелік; `ENUM` складніше змінювати міграцією.
- `hla_typing` як `TEXT[]`: набір типування це впорядкований список маркерів, який читається і замінюється цілком;
  окрема таблиця для лабораторної зайва.
- `registered_on` як `DATE`: час внесення не потрібен.
- `available` як `BOOLEAN`: два стани.
- Правило віку перевіряє сервіс (400 з поясненням); `CHECK` на роках 1900..2100 і на перелік групи крові це другий
  рубіж, щоб сміття не потрапило в таблицю повз сервіс.

## 2. Проєктування API

Формат помилки валідації: `{"errors":[{"field":"birth_year","message":"..."}]}`.
Формат переліку: `{"items":[...],"total":N,"limit":L,"offset":O}`.
`limit` за замовчуванням **20**, верхня межа **100**; значення понад межу дає **400** (не мовчазне обрізання),
`offset >= 0`. Ідентифікатор не передається в тілі: зайві поля (`id` теж) відхиляються з 400.

| Ендпоінт | Тіло запиту | Тіло відповіді | Успіх | Помилки |
|---|---|---|---|---|
| `POST /donor-registry` | `donor_code`, `birth_year`, `blood_group`, `hla_typing`, `registered_on`, `available` | створений запис з `id` | 201 | 400 невалідні дані (поле і причина); 409 дубль `donor_code` |
| `GET /donor-registry?limit&offset&available` | немає | `items`, `total`, `limit`, `offset` | 200 | 400 некоректні параметри |
| `GET /donor-registry/{id}` | немає | запис | 200 | 404 не знайдено; 400 `id` не число |
| `PUT /donor-registry/{id}` | усі 6 полів (повна заміна) | замінений запис | 200 | 400 невалідні дані; 404; 409 дубль `donor_code` |
| `DELETE /donor-registry/{id}` | немає | немає тіла | 204 | 404 (також при повторному видаленні) |
| `GET /healthz` | немає | `{"status":"ok"}` | 200 | 503 база недоступна |

Валідація віку: `поточний рік - birth_year` має бути від 18 до 55 включно, інакше 400 з полем `birth_year` і поясненням.
`/healthz` виконує `SELECT 1` у базі із таймаутом 2 с, тому перевіряє саме доступність бази, а не лише живий процес.
Перевірено зупинкою бази:

```
docker compose stop db
спроба 1: HTTP 503  тіло: {"status":"unavailable"}
спроба 2: HTTP 503  тіло: {"status":"unavailable"}
спроба 3: HTTP 503  тіло: {"status":"unavailable"}
GET /donor-registry -> 500        (звичайний ендпоінт при недоступній базі)
docker compose start db           -> /healthz знову 200
```

Сервіс не тримає стану в пам'яті процесу (пул з'єднань стану даних не містить), усе зберігається в базі.

## 3. Етапи 2-4. Реалізація, образ, стенд

- **Сервіс** (`app/main.py`): FastAPI, `psycopg_pool.AsyncConnectionPool`. Помилки валідації pydantic перетворюються
  на 400 (за замовчуванням FastAPI віддає 422). Під час старту пул чекає на базу до 60 с; `/healthz` у цей час віддає
  503, тому запит, що прийшов у перші секунди після `up`, отримує відповідь, а не помилку підключення.
- **Образ**: багатоетапна збірка, залежності ставляться у venv у builder-стадії; у фінальній стадії лише venv і код,
  без компіляторів, `pip`-кешу, `curl` і `wget`. Процес працює від користувача з фіксованим uid 10001.
- **Стенд**: три сервіси `db`, `web`, `lb`. Порт на хост публікує лише `lb`. Кількість вебінстансів задається змінною
  `WEB_REPLICAS` (`deploy.replicas`), без правок у файлах. Схема накочується монтуванням `db/schema.sql` у
  `/docker-entrypoint-initdb.d`. `web` залежить від `db` за станом `service_healthy`, `lb` від `web`.
  Пароль бази лише в `.env` (у репозиторії `.env.example`, `.env` у `.gitignore`).

Перевірено, що стенд піднімається **однією командою** і з одним, і з двома інстансами, без правок у файлах:

```
docker compose down -v
WEB_REPLICAS=2 docker compose up -d      # одна команда
перший запит одразу після up: GET /healthz -> 200 {"status":"ok"}
200 запитів поспіль -> розподіл 100 / 100 між донорськими інстансами, без перезапуску балансувальника
```

Окремий випадок: якщо кількість реплік змінюють на **вже запущеному** стенді, nginx тримає адреси, отримані під час
свого старту, тому потрібен `docker compose restart lb`. При підйомі з нуля цього не потрібно, бо `lb` стартує після
того, як усі вебінстанси стали `healthy`.

### Dockerfile

```dockerfile
# syntax=docker/dockerfile:1

# ---- builder: тут ставляться залежності, у фінал іде лише готовий venv ----
FROM python:3.12-slim AS builder
ENV PIP_NO_CACHE_DIR=1 PIP_DISABLE_PIP_VERSION_CHECK=1
RUN python -m venv /opt/venv
COPY requirements.txt .
RUN /opt/venv/bin/pip install -r requirements.txt

# ---- final: без компіляторів, pip-кешу і curl/wget ----
FROM python:3.12-slim
ENV PATH=/opt/venv/bin:$PATH PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1
RUN useradd --system --uid 10001 --no-create-home app
COPY --from=builder /opt/venv /opt/venv
WORKDIR /srv
COPY app ./app
USER 10001
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--no-access-log"]
```

### lb/nginx.conf

```nginx
worker_processes auto;

events {
    worker_connections 4096;
}

http {
    # $upstream_addr показує, на який інстанс пішов запит
    log_format lb '$time_iso8601 "$request" $status upstream=$upstream_addr '
                  'urt=$upstream_response_time rt=$request_time';
    access_log /dev/stdout lb;

    # web резолвиться під час старту у всі IP реплік (DNS Compose), далі round-robin.
    # Після зміни кількості реплік lb треба перезапустити (див. README).
    upstream web {
        server web:8000;
        keepalive 64;
    }

    server {
        listen 80;

        # ендпоінт, який нічого не робить: для перевірки самого генератора навантаження
        location = /_null {
            access_log off;
            default_type text/plain;
            return 200 "ok\n";
        }

        location / {
            proxy_pass http://web;
            proxy_http_version 1.1;
            proxy_set_header Connection "";
            proxy_set_header Host $host;
        }
    }
}
```

## 5. Етап 5. Вимірювання під навантаженням

### Генератор

`loadgen/gen.py`, лише стандартна бібліотека. Відкритий контур: задана інтенсивність ділиться між процесами; кожен
процес наперед обчислює моменти відправки `t = k/rate + i*procs/rate` від початку прогону і віддає запит пулу
потоків, тож цикл планування не чекає на відповідь. Закритий контур: фіксована кількість «віртуальних користувачів»,
кожен шле наступний запит після відповіді на попередній (до 500 користувачів потоками, далі корутинами asyncio,
бо тисячі потоків упираються в стек і перемикання контексту).

### Сценарій і команди

Вимірюється `GET /donor-registry/{id}`. Перед серією `loadgen/seed.py` заносить 100 записів, ідентифікатори беруться
з них. Рівні 10, 100 і 500 rps за завданням, додатково 700, 800 і 1000, щоб побачити межу. Прогрів 10 с +
вимірювання 30 с, 3 повтори на рівень, у таблицю медіана. Команди (з кореня репозиторію):

```bash
python loadgen/run_series.py selfcheck               # перевірка генератора проти /_null
python loadgen/run_series.py series --instances 1    # 10, 100, 500 rps x 3 повтори
python loadgen/run_series.py series --instances 2
python loadgen/run_series.py series --instances 1 --rates 700 800 1000 --stats
python loadgen/run_series.py series --instances 2 --rates 700 800 1000 --stats
python loadgen/run_series.py distribution            # розподіл між двома інстансами
python loadgen/run_series.py closed --rate 700       # закритий контур
python loadgen/aggregate.py && python loadgen/calc.py
```

## 7. Висновок про межу пропускної здатності і ефект другого інстанса

**Один інстанс.**

- 10 і 100 rps: сервіс тримає ціль, p95 приблизно 6-7 мс, у системі в середньому менше одного запиту (L = 0,4).
- **500 rps: інтенсивність ще тримається** (501,7 із 500), **але затримка вже зламана**: p50 59,8 мс, p95 948 мс,
  p99 1115 мс (на 100 rps p95 було 6,7 мс); середня кількість запитів у системі виросла з 0,4 до 110, максимум 591.
- **700 rps: рівень, на якому один інстанс перестає тримати задану інтенсивність.** Досягнуто 537 із 700
  (повтори 552 / 537 / 489), p50 8,0 с, p95 11,6 с, L приблизно 4163. Усі запити при цьому отримали відповідь.
- 800 і 1000 rps: досягнуто 470 і 540 rps, p50 16,8 і 19,0 с, і вже 28 % та 36 % запитів не встигли завершитись.
- Отже, пропускна здатність одного інстанса приблизно **540-640 rps** (верхня оцінка з закритого контуру при
  110 одночасних запитах: 642 rps). За даними `docker stats` процес `web` у цей час на 91-96 % свого ліміту в 1 CPU,
  база (16 %) і nginx (13 %) далекі від насичення, а хост завантажений у середньому на 59 %. Обмежувала
  обчислювальна потужність самого вебінстанса (ліміт 1 CPU).

**Чому час відповіді зростає швидше за інтенсивність.** Поки завантаження нижче одиниці, запит майже не чекає
(p50 близько 3 мс і на 10, і на 100 rps). Біля межі середній час очікування в черзі зростає приблизно як
`1/(mu - lambda)`, де `mu` це пропускна здатність, `lambda` це інтенсивність; тому зростання інтенсивності зі 100 до
500 rps (у 5 разів) збільшило p95 приблизно у 140 разів. Коли `lambda` перевищує `mu`, черга росте весь час прогону,
і затримка обмежена лише тривалістю прогону та таймаутом, а не властивостями сервісу.

**Два інстанси.**

- 500 rps: p50 впав із 59,8 до 3,7 мс, середній час відповіді з 219 до 116 мс, L зі 110 до 58. Але **p99 не
  змінився** (приблизно 1,1-1,2 с), а p95 впав лише з 948 до 638 мс.
- 800 rps: два інстанси утримали 784 rps без жодного незавершеного запиту (один інстанс 470 rps). Проте перший
  повтор дав лише 640 rps, а два інших 785.
- 1000 rps: обидві конфігурації перевантажені, 540 проти 591 rps (повтори 664 / 591 / 432).
- На 500 rps і з одним, і з двома інстансами спостерігаються періодичні зупинки: приблизно кожні 9-10 с на 3-4 с
  затримка стрибає до 1 с, потім повертається до 3 мс. Причину не встановлено; вона однакова для обох конфігурацій.

**Яка складова лишилась спільною.** Пропускна здатність не подвоїлась (максимум 784 rps проти 1080 теоретичних).
Дані `docker stats` і лічильників Windows (`results/stats/`, `results/host_*.csv`) на рівні 1000 rps:

| | 1 інстанс | 2 інстанси |
|---|---|---|
| CPU кожного `web` | 91-96 % | 90-102 % |
| CPU бази | 16 % | 30 % |
| CPU nginx | 13 % | 30 % |
| CPU хоста, медіана під навантаженням | 59 % | **85 %** (39 зі 105 замірів вище 90 %) |

Обидва `web` упираються у свій ліміт, а база й nginx ні, тож спільним обмежником є **обчислювальна потужність хоста**:
на тих самих 8 ядрах працюють генератор (4 процеси), два вебінстанси, nginx, Postgres і VM Docker Desktop.
Можливий додатковий чинник (припущення, окремо не вимірювалось): у перевантаженні сервер витрачає процесор на запити,
які клієнт уже кинув за таймаутом. Базу як вузьке місце дані не підтверджують.

## 8. Етап 7. Розрахунки

### 8.1. Прискорення і метрика Карпа-Флатта (N = 2)

`S = X2 / X1` на тому самому рівні інтенсивності; `e = (1/S - 1/N) / (1 - 1/N)`, для N = 2: `e = (1/S - 0,5) / 0,5`.

| Рівень, rps | X1 | X2 | S | e |
|---|---|---|---|---|
| 500 | 501,7 | 499,9 | 0,997 | 1,007 |
| 800 | 470,5 | 784,0 | 1,666 | 0,200 |
| 1000 | 539,6 | 590,6 | 1,095 | 0,827 |

Підстановка для 800: `S = 784,0 / 470,5 = 1,666`; `1/S = 0,600`; `e = (0,600 - 0,5) / 0,5 = 0,200`.
Для 1000: `S = 590,6 / 539,6 = 1,095`; `1/S = 0,913`; `e = (0,913 - 0,5) / 0,5 = 0,827`.

Що це означає:

- На 500 rps обидві конфігурації досягли заданих 500 rps, тому `S` близьке до 1 це відношення **заданих** значень,
  а не потужностей. Це не вимірювання прискорення, і в підсумок воно не береться.
- Змістовні рівні це 800 і 1000: **S приблизно 1,1-1,7, частка нерозпаралеленої роботи e приблизно 0,2-0,8.**
  Розкид великий, бо в режимі перевантаження результат нестабільний (див. розділ 0).
- Значення `e`, близьке до 1, означає, що друга репліка майже не додала. Спільною для обох інстансів лишилась
  обчислювальна потужність хоста. Якби база була не одна на два інстанси, `e` змінилось би мало, бо база не насичена
  (16-30 % CPU); суттєвіше `e` знизилось би, якби кожен інстанс отримав власні ядра.

### 8.2. Закон Літтла (100 rps, 1 інстанс)

`L = lambda * W`. Підстановка: `lambda` = 100,00 rps; `W` = 3,87 мс = 0,00387 с; `lambda * W = 100 * 0,00387 = 0,3875`;
виміряне `L` (середня за вікном різниця між відправленими і завершеними) = 0,3875; **розбіжність 0,00 %**.

Це майже тавтологічна збіжність: `L` і `W` рахуються з одних і тих самих записів, а на низькому навантаженні немає
крайових ефектів. Змістовніша перевірка на рівні 500 rps (1 інстанс, медіани): `lambda` = 501,7 rps; `W` = 219,1 мс;
`lambda * W = 109,9`; виміряне `L` = 109,7; розбіжність приблизно 0,2 %.

### 8.3. Відкритий і закритий контур

Повторено на рівні, де сервіс уже не тримає задану інтенсивність (700 rps: досягнуто 537 із 700). Кількість
одночасних запитів у закритому контурі дорівнює середньому `L`, яке спостерігалось у відкритому контурі на цьому
рівні. Для порівняння наведено також рівень 500, де сервіс ще тримає інтенсивність, і рівень 800.

| Рівень (відкритий контур) | Контур | Одночасних запитів | Досягнуто, rps | p95, мс | Не-2xx, % |
|---|---|---|---|---|---|
| 500 rps | відкритий | L ≈ 110 | 501.7 | 948.4 | 0.00 |
| 500 rps | закритий | 110 | 642.1 | 354.4 | 0.00 |
| 700 rps | відкритий | L ≈ 4163 | 536.9 | 11606.5 | 0.00 |
| 700 rps | закритий | 4163 | 343.8 | 9969.0 | 0.00 |
| 800 rps | відкритий | L ≈ 8213 | 470.5 | 22745.1 | 28.16 |
| 800 rps | закритий | 8213 | 265.4 | 26566.0 | 49.78 |

Чому закритий контур показує меншу затримку на тому самому сервісі. У закритому контурі клієнт не надсилає новий
запит, доки не отримав відповідь на попередній, тому кількість запитів у системі жорстко обмежена і черга не може
рости: сервіс сам гальмує джерело навантаження. У відкритому контурі запити надходять за розкладом незалежно від
відповідей, і в моменти уповільнення черга накопичується (на рівні 500 L_max досяг 591 при середньому 110), що й дає
високі перцентилі. За законом Літтла середній час відповіді в закритому контурі дорівнює `W = N / X`: при N = 110 і
X = 642 це 171 мс. Саме тому генератор із фіксованою кількістю користувачів **приховує перевантаження**: скільки б
сервіс не гальмував, кількість запитів у польоті не зростає.

Два зауваження до таблиці, які не можна замовчувати:

- На рівні 700 закритий контур дав **меншу** пропускну здатність (344 проти 537 rps) при меншому p95. Це не
  властивість сервісу, а наслідок того, що 4163 одночасних з'єднання самі по собі стають навантаженням: клієнт
  тримає 4163 корутини, а сервер 4163 відкритих сокети.
- На рівні 800 потрібні 8213 одночасних з'єднань, і на цьому стенд ламається: nginx повертає 502 і 504, частина
  з'єднань узагалі не встановлюється (половина запитів не-2xx). Це межа інфраструктури (Docker Desktop, nginx,
  ліміти з'єднань), а не вимірювання сервісу, тому основним вважається рівень 700.

## 11. Відкинуті рішення

1. **Кілька процесів `uvicorn --workers N` всередині контейнера.** Ліміт контейнера 1 CPU, а масштабування за
   завданням має робитись окремими інстансами за балансувальником; кілька воркерів ховали б межу одного інстанса
   і заважали б вимірювати прискорення.
2. **`curl` або `wget` у образі для healthcheck.** Порушує додаткову вимогу варіанта і збільшує образ; замість цього
   перевірку виконує інтерпретатор Python, який в образі вже є.
3. **Схема з коду сервісу під час старту (`CREATE TABLE IF NOT EXISTS` у застосунку).** Два інстанси стартують
   одночасно і конкурують за DDL. Обрано монтування `db/schema.sql` у `/docker-entrypoint-initdb.d`: накочується рівно
   один раз, на порожньому томі.
4. **`ENUM` у PostgreSQL для групи крові.** Зміну переліку складніше проводити міграцією; `TEXT` з `CHECK` простіший
   і достатній.
5. **DNS-резолвінг nginx на кожен запит (`resolver` і змінна в `proxy_pass`).** Робить `keepalive` до upstream
   неможливим і додає накладні витрати на кожен запит; обрано статичний `upstream` з `keepalive 64`, ціною
   перезапуску `lb` при зміні кількості реплік на вже запущеному стенді.
6. **Обрізання `limit` до максимуму замість 400.** Мовчазна зміна параметра приховувала б помилку клієнта;
   обрано явний 400 з поясненням.
7. **Готові інструменти навантаження (wrk, k6) з фіксованою кількістю віртуальних користувачів.** Вони працюють у
   закритому контурі й приховують затримку під перевантаженням; завдання вимагає власного генератора з фіксованою
   швидкістю надходження.
8. **Потоки для закритого контуру на тисячах користувачів.** 4000-8000 потоків упираються в пам'ять під стеки і
   перемикання контексту, тому для великої кількості користувачів використано корутини asyncio.

## 12. Використання генеративних моделей

Модель Claude (Anthropic, через Claude Code) використана для: каркаса сервісу (`app/main.py`, `db/schema.sql`),
`Dockerfile`, `docker-compose.yml` і `lb/nginx.conf`, генератора навантаження та скриптів вимірювання
(`loadgen/`, `scripts/`), а також для чернетки цього звіту й інтерпретації результатів.

Що перевірено після моделі (запуском, а не читанням коду):

- повний цикл запитів із кодами 201/400/404/409/204 і повторним DELETE -> 404 (розділ 9), збереження даних після
  `down` і порожня база після `down -v`;
- що `/healthz` справді віддає 503 при зупиненій базі, а не лише перевіряє живий процес (розділ 2);
- що стенд піднімається однією командою і з одним, і з двома інстансами, і що на свіжому стенді запити одразу
  розходяться між репліками (розділ 3 і 6);
- відсутність `curl`, `wget` і `gcc` в образі, uid процесу, ліміти CPU і пам'яті, відсутність пароля в образі,
  історії збірки й репозиторії, недоступність портів бази і вебінстансів з хоста (розділ 10);
- що генератор тримає ціль 500 і 1000 rps проти порожнього ендпоінта (розділ 5);
- збіжність закону Літтла (розділ 8.2) і розподіл запитів між двома інстансами двома незалежними способами (розділ 6);
- цілісність сирих даних: усі файли прогонів перевірено на сторонні відповіді після виявлення колізії порту 8080
  (розділ 0).

Чесність висновків перевірялась окремо: у розділах 0, 7 і 8.3 прямо зазначено, де результат нестабільний, де число
є припущенням, і що причину періодичних зупинок на рівні 500 rps встановити не вдалось.
